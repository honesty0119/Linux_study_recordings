# 任务05阶段总结

## 目标与范围调整

原目标是在Linux板端提供Web状态展示、SQLite配置/运行历史及Modbus TCP/RTU只读状态上报。用户将平台改为现有RK3568，实际网络采用Wi-Fi。没有USB转RS485及已核实的实体链路，用户明确当前只做TCP，RTU暂缓。

标准Modbus服务器是请求响应：主站轮询，板端回复状态。本实现不做无请求主动推送，不执行继电器/IO控制，不接受Modbus写线圈或寄存器。Web独立配置接口的保存能力不等于允许Modbus写控制。

## 实施过程

1. 核对AArch64 ABI、既有交叉工具链和依赖，完成libmodbus/SQLite依赖验证。
2. 用C读取内核网络状态，发布互斥保护的快照，提供FC03只读TCP服务。
3. 单写线程将历史写入SQLite，实时读取和历史查询分离。
4. C SCGI API与独立nginx实例提供只读页面、历史分页、趋势和事件。
5. 私有配置API增加令牌、Origin、参数和revision保护，区分保存值与实际启动加载值。
6. 增加只读C主站、严格响应校验、启停工具，完成真实TCP通信和30分钟稳定性测试。

## 两个已解释的问题

历史页面每页最多50条，不代表数据库最多只有50条。通过记录编号、翻页和更新提示澄清；稳定信号的曲线接近水平，也不代表停止采集。

主机诊断曾在服务shutdown后查询getpeername，造成日志peer_port=0、断言无法匹配。已改为accept4时保存端口，停止和RST回归通过。更早一次没有完整日志的EOF仍无法追溯，不能用此修复声称解释了所有旧故障。

## 结果与证据强度

真实开发板监听TCP502，Windows通过局域网读取；六类写请求返回异常01。新增C主站在板内运行，验证AArch64可执行和真实状态解码；外部网络通信由Windows协议客户端验证，两者不混称。

30分钟：1800.018秒，3客户端各1800次读取，零错误/重连；p50 52.10ms、p95 222.31ms、p99 382.67ms、最大846.77ms；最大快照年龄1010ms。全部原始请求记录在本地核对5400条；公开提供汇总、首尾样本、服务器日志和资源采样。

## 收尾决定

用户确认以当前TCP目标收尾。代码与验收通过不等于用户独立掌握已考核；后续可阅读源码、复述状态快照/协议/持久化原理。常驻部署、自启、备份恢复及RTU不再作为本轮必做步骤，也不通过新增实验扩大收尾范围。
