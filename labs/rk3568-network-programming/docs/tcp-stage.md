## 对照原文的实现

| 原文要求 | 当前实现位置与行为 |
| --- | --- |
| 主线程采集、连续稳定 10ms、只报告按下 | board/key_network.c；约 2ms 采样驱动状态，同时消费 evdev 边沿；board/task2_core.h 对按下和释放均确认稳定 10ms。长按不重复，启动时已按住须先释放 |
| 消息队列解耦主线程和网络线程 | 每次运行创建独立 System V 队列，mtype=2；主线程封装按键帧入队，网络线程消费；退出移除自己的队列 |
| 无按键也每 1s 心跳 | 网络线程用 CLOCK_MONOTONIC 截止时间调度；心跳不依赖按键，连续按键也每轮检查心跳 |
| TCP 主动连接、断开后每秒重试 | 非阻塞 connect/send/poll；连接尝试超时 1s，失败后约每秒重试；已连接后的断开立即开始重连 |
| 心跳 6 字节、按键 8 字节、XOR | task2_core.h 逐字节编码；Unix 秒数采用大端；不直接发送 C 结构体 |
| Windows 接收、解析、日志 | host/Receiver.cs，使用 Windows 已有 .NET Framework 编译；严格处理拆包/合包与校验 |
| 超过 2s 无心跳报警 | Stopwatch 单调时钟，约 20ms 检查一次；只有合法心跳刷新，按键不刷新；断开后仍保留计时直到报警 |

逻辑 KEY0 映射到 adc-keys 的 KEY_VOLUMEUP（Linux code=115）；默认 /dev/input/event7，程序会检查该设备支持 code=115。不要用会触发休眠的电源键。重启导致 event 编号变化时，先核对设备。

## 线程、队列与故障策略

- 原文“阻塞读取队列”与“无事件也定时心跳”不能由无限阻塞的 msgrcv 同时满足。本实现用 IPC_NOWAIT 和 eventfd 唤醒，有界 poll 等待，仍使用真实 System V 队列传递报文。
- 断线时尚未消费的按键留在有界队列中；恢复后按序发送，因此可能收到旧按键，线上时间戳仍为事件确认时刻。队列满会明确报错并停止，不无限阻塞采集或静默丢弃。
- 每次只发送一帧，处理部分 send，禁止两帧交错；发送停滞 500ms 会关闭并重连。已经从队列取出、发送结果不明确的帧记入 uncertain，不自动重放。
- 原协议没有事件序号或应用层 ACK，不能承诺跨断线绝不丢失/重复；socket_sent 只证明内核接受，不证明 Windows 已处理，必须对照接收端计数。
- 退出不会无限等待断网队列排空，打印 pending/uncertain；有未完成数据时返回非零并清理本程序队列。不要将 INCOMPLETE 当成验收通过。
- 心跳按绝对周期调度，错过的历史心跳不集中补发。断线时不可能向失效 TCP 连接成功发送；重连后立即发新心跳。网络阻塞/调度延迟下不能保证传输实时性。
- 使用 TCP_USER_TIMEOUT=3000ms（内核支持时）帮助发现未确认数据，FIN/RST 可直接检测；“物理断网后即时发现”“恢复链路后必然 1s 内连接”仍须实际测试，不能由重试间隔推导。
- 仅接受原协议类型、长度、KEY0/按下和 XOR。TCP 没有同步头，遇非法帧关闭该连接后继续监听，不猜测重同步位置。半帧不输出，断开会说明有残帧。
- XOR 是简单错误检测，不提供防篡改能力。系统时间仅供显示；两端单调时间属于不同基准，不能直接相减算网络延迟。

Ubuntu 构建与检查命令放在本任务 commands.txt。已完成的构建不等于真实按键和长期稳定性验收。

Windows 本机运行副本为 <LOCAL_WORKSPACE>\.local\task2-host\Receiver.exe，源代码和归档产物保存在本任务目录。Samba 上 exe 直接启动曾被拒绝，使用本机副本运行，未降低执行策略。Windows PowerShell 运行：

```powershell
& '<LOCAL_WORKSPACE>\.local\task2-host\Receiver.exe' 192.0.2.20 8888 --log ('<LOCAL_WORKSPACE>\.local\task2-host\tcp-' + (Get-Date -Format yyyyMMdd-HHmmss) + '.log')
```

以上启动长期监听，Ctrl+C 停止。可在最后追加秒数，限定实验时长。不要同时启动两个占用 8888 的实例。

开发板 Linux shell 运行（当前部署；重启后 /tmp 可能消失）：

```sh
/tmp/rk3568-tcp-v2.TjKBKF/key_network 192.0.2.20 8888 /dev/input/event7
```

Ctrl+C 停止。程序也支持在最后追加运行秒数。--heartbeat-only 秒数只发送心跳；--synthetic 秒数每 200ms 合成一次按键并经过同一消抖、队列与网络链路，不能算物理按键验收。

## 验收分层

1. 确定性逻辑：协议黄金字节、10ms 边界、抖动、稳定释放、长按；已在 RK3568 运行 24 项通过。
2. Windows 接收端：28 项自测；回环 TCP 的分段/合帧、非法帧关闭、重新连接和超时恢复已通过。持续按键不刷新心跳，超时约 2013/2016ms。
3. 真实 Wi-Fi 合成数据：首轮 43 个事件入队/发送/接收一致，9 个心跳，接收间隔 972–1070ms，心跳超时 2004.562ms。
4. 上位机停止/重启：首轮已观察断线、约每秒重试、重新接收心跳；接收程序重启后约 891ms 建立连接。这是应用关闭测试，不等于物理 Wi-Fi 断网测试。
5. 实际用户键：本阶段集成版重测已通过当前 4 次样本，原始按下/释放各 4 条，入队/发送/Windows 接收均 4 条；4 次按住时间为 309.824、206.400、206.571、936.452ms。首轮仅 3 条的结果保留，用户表示可能少按一次。
6. 性能/稳定性：物理按下→入队 ≤50ms、发送→解析 ≤100ms、接收→日志 ≤50ms 仍需可比时钟/明确测量；至少 1 小时稳定性尚未执行。

首轮重连后的接收间隔曾出现 892.413ms，低于 900ms。板端发送日志相邻约 1000ms；Wi-Fi 到达抖动需继续记录，不能宣称全部时间指标已通过，也不为改善数字而删除异常样本。

## 本轮收尾结果

- 真实重测持续约 110s，板端发送 110 个心跳，发送日志间隔 999–1001ms；Windows 收到 110 个心跳和 4 个按键事件。
- Windows 心跳间隔为 801.289–1266.579ms，共 109 个间隔中 10 个超出 900–1100ms。因此发送周期当前样本正常，但到达周期指标没有全部通过，不能宣称整体性能达标。
- 心跳停止后 2014.037ms 报警；板端退出汇总 enqueued=4 socket_sent=4 pending=0 uncertain=0 status=OK。队列列表恢复为空，无 key_network/capture_input 进程遗留；Windows 测试监听已退出。
- 原始事件被独立记录程序观察到至入队为 12/11/11/11ms。这是同板软件观察值，未测量物理触点到驱动的延迟，也未证明跨机器端到端延迟。
- 汇总证据 logs/tcp/physical-result.json，原始日志 physical2-raw.log、physical2-board.log、physical2-host.log；首轮 physical-* 与两轮合成/reconnect 日志均保留。
- 接收端补充处理：若旧 TCP 未收到 FIN/RST 但心跳已超时，新连接可替换旧连接，避免阻塞恢复后的连接。最终接收端重新编译并通过 28 项自测及回环测试，回环中验证了超时旧连接替换；本分支仍需实际物理断网场景复核。
- 限定的 Windows 防火墙规则按用户授权保留，未自动删除；本轮无新的 Ubuntu 待执行命令。源码、产物、说明均已保存，未发布学习仓库。
