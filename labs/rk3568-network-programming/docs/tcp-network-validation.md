## 真实无线断开与恢复

用户明确授权后，通过 ConnMan 关闭开发板 Wi-Fi 约 8s，再启用并连接原先保存的目标网络。脚本脱离 SSH 运行，附带独立恢复进程。Windows 无线连接不变；未修改密码、路由器、电源策略、网卡高级设置或已有防火墙规则。

原始记录确认离线时 iw 输出 Not connected、wlan0 没有 IPv4；恢复后回到原 SSID 和地址。不是仅关闭接收程序模拟断网。

| 测量项目 | 首轮旧版 | 第二轮修正版 |
| --- | ---: | ---: |
| 发出关闭 Wi-Fi 请求→板端发现断线 | 5820ms | 101ms |
| 关闭命令返回→板端发现断线 | 5718ms | 13ms |
| Windows 距最后有效心跳报警 | 2001.800ms | 2017.454ms |
| 重新启用 Wi-Fi 命令返回→TCP 新连接建立 | 725ms | 2072ms |
| 自动恢复接收心跳、替换超时旧连接 | 通过 | 通过 |

这里“启用 Wi-Fi”不等于“已经完成无线关联并拿到 IP”。前两轮恢复状态每 2s 观察一次，不能把它们直接当成原文“网络已恢复后 1s 内连上”的精确验收。另做约 100ms 观测的短测，结果见本文末尾；仍不能由一次成功推出所有网络条件下都保证 1s。

断线期间 send 成功只表示内核接受，不能声称 Windows 收到。原协议没有应用 ACK，断网期间的心跳可以丢失，无法发到不存在的连接。按键跨断线的交付边界仍按 tcp-stage.md 所述处理。

## 心跳抖动的证据

采用板端 tcpdump 和 Windows PktMon，只针对本实验板地址与 TCP 8888 流量。采集结束停止抓包并移除临时 PktMon 筛选器。捕获文件保留在任务 logs 下，不发布到公开学习仓库。

1. 板端程序日志及 tcpdump 均支持发送周期稳定。timing3 中配对的 22 个心跳，其 21 个板端出站间隔为 999.184–1000.836ms。
2. 同一批心跳在 Windows WFP 802.3 捕获点（无线驱动转换之后、应用之前）的间隔为 890.562–1075.583ms，已经出现超过 ±100ms 的样本；应用日志显示基本相同的变化。因此这批抖动发生在应用解析之前，尚不能继续区分无线空口、AP 缓冲和驱动处理。
3. 更长的 timing2 样本中，板端抓包间隔为 999.022–1000.943ms，而 Windows 应用间隔约 812–1199ms。板端数据到 ACK 的 RTT 约 47–286ms，包含 Windows 延迟 ACK，不能当作单向传输延迟。
4. timing3 中接收→完整日志写完最大 32.618ms；修正版断网轮次最大 41.860ms，均在当前样本的 50ms 目标内。接收解析约 2ms，不是约 200ms 抖动的直接解释。
5. 早期统计的 max_log_ms 包括启动、监听和状态日志，不等同于“收到报文→写完该报文日志”。后续已单独记录 max_receive_to_log_ms，避免混用指标。

Windows 抓包时间和 DateTime.UtcNow 时间存在约 1ms 量级差异，部分相减结果约 -0.9ms。负数不是负延迟，不能用它宣称亚毫秒精度；只用同一时间源的间隔比较。板端与 Windows 时钟未做精确同步，仍未证明单向发送→解析 ≤100ms。

前两次文件模式 PktMon 只有计数、无 packet 事件；对应文件不作为有效 Windows 抓包证据。后改用内存模式和默认捕获 flags，获得有效 packet 事件。timing3/windows-all.pcapng 保留全部采集组件，windows.pcapng 是组件 36 的筛选结果；同一包的重复观测按 TCP 序号、端口和载荷去重。23 个应用心跳中 22 个与板端捕获配对，捕获启动窗口不包含第一帧，不能据此认定丢包。
