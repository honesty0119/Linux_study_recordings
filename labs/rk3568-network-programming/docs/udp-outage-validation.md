## 实验方法与真实离线证据

上位机连续运行 UDP 接收器，板端 key_udp 运行 55 秒，持续产生合成按键并按 1Hz 调度心跳。板端测试任务脱离 SSH 运行，先保留约 10 秒正常基线，再使用 ConnMan 关闭 Wi-Fi；恢复过程另有独立看门狗。自动恢复只连接已经保存的原网络，不创建新网络配置。

outage-control.log 中 disable_result 返回成功，offline_state 同时记录 `Not connected.` 和空 IPv4 地址。约 8008ms 后发出恢复请求，之后观测到原网络及原 IPv4 恢复。这是真实无线接口断开，不是关闭上位机或暂停发送程序模拟离线。

板端最终退出码为 1，状态为 INCOMPLETE。这是当前程序对“有入队事件未成功发送”的如实报告，不是把断网实验中的丢失隐藏为成功。发送线程没有因预期网络错误提前退出，恢复后继续发送直至既定时限；273 = 229 + 44。因而可以判定**断网恢复功能通过**，同时保留**该次运行并非全部事件送达**的事实。

UDP 没有 connect/重连/应用重传。网卡恢复后沿用原数据报 Socket 继续 sendto，心跳重新出现让上位机恢复正常状态；不存在 TCP 式重新建立连接。合成按键仅用于验证队列和网络恢复，不替代已有的真实物理按键测试或物理响应时间测量。

## 首轮编排问题与修正

首轮证据保存在 logs/udp-outage/20261122-192057。SSH 执行 shell 后台启动命令时返回超时，旧编排在异常处理中提前停止了 Windows 接收器。板端任务实际上已经启动，并完成断网及自动恢复，因此没有立即重复触发断网，而是先确认它结束和网络恢复。由于接收日志不完整，该轮不作为完整功能验收。

tests/test_udp_wifi_outage.py 已改为通过 Python Popen 明确关闭继承的 SSH 描述符、创建独立会话；若 SSH 返回超时，也不重发请求或提前停止接收，而是保留接收器、等待恢复后取证。修正后在新目录完整复测得到上述结果。没有修改 UDP 生产程序来掩盖测试问题。
