## 3. 架构与关键设计

```text
RK3568 主线程
  adc-keys 状态/边沿 → 约 2ms 采样 → 连续稳定 10ms → 有效按下
                                                    ↓ 编码
                                      System V 消息队列（按键帧）
                                                    ↓
RK3568 网络线程：消费按键 + 独立调度每秒心跳 → TCP 或 UDP
                                                    ↓
Windows：接收 → 校验/解析 → 更新有效心跳时刻 → 有界日志队列
                  ↓                              ↓
             超过 2s 报警                 独立写线程 → 文件/Flush
```

**按键消抖。** 按下和释放都要确认稳定 10ms；按住期间不重复触发，稳定释放后才接受下一次按下。启动时已经按住的键须先释放。原始输入边沿、消抖确认、入队和 Windows 日志是不同观测点，不能混作物理触点发生时刻。

**队列解耦。** 每次运行创建独立 System V 队列，按键消息 `mtype=2`，退出清理自己的队列。它在本任务中连接同一进程的两个线程，虽然也可用于进程间通信。网络线程使用 `IPC_NOWAIT`、`eventfd` 唤醒和有界等待；若无限阻塞在空队列上，无按键时就无法及时发心跳。队列满时明确失败，不能无限积压或静默丢弃后报成功；板端队列压力验收仍需补齐。

**心跳独立调度。** 板端使用 `CLOCK_MONOTONIC` 绝对截止时间，处理按键时也检查心跳，不集中补发过期心跳。Windows 使用单调时钟检测距离最后合法心跳的时长，约每 20ms 检查；按键、坏包和错误来源不能刷新心跳。心跳表示“近期收到了有效报文”，超时并不能独自区分进程停机、无线中断、丢包或调度阻塞。

**日志独立输出。** 接收线程将日志放入容量 1024 的有界队列，独立线程按 FIFO 写本地文件并 Flush。满队列、写失败或退出不能排空均明确报错。验收计时覆盖解析、格式化、排队、输出和 Flush 返回，不能只测入队速度。这里的完成指写入调用返回，不等于屏幕绘制完成或物理磁盘持久化。

## 4. 线上协议与解析

| 帧 | 字节布局 | 长度 |
| --- | --- | ---: |
| 心跳 | `01` + 4 字节 Unix 秒数 + XOR | 6 字节 |
| 按键 | `02 00 01` + 4 字节 Unix 秒数 + XOR | 8 字节 |

时间戳按 32 位无符号数、大端编码；最后一字节为此前所有字节异或。逐字段编码，避免直接发送 C 结构体带来的填充和字节序问题。按键时间戳对应软件确认事件时刻，不能当作已精确测得的物理触点时间。协议的秒级时间戳用于显示，无法验证 50/100ms 指标。

TCP 是字节流，一次接收可能只有半帧，也可能含多帧；接收器缓存后按类型和固定长度拆分，非法帧关闭连接，半帧不输出。UDP 保留数据报边界，本实现一包恰好一帧；拒绝跨包拼接、多帧合包、尾随字节、坏校验和错误来源 IP，允许板端重启后源端口变化。来源 IP 筛选不等于身份认证。

## 5. TCP 与 UDP 的实际区别

| 比较项 | TCP 版本 | UDP 版本 |
| --- | --- | --- |
| 建立通信 | 板端主动连接 Windows 监听端口 | `sendto` 指定目标；Windows `ReceiveFrom`，无握手 |
| 数据边界 | 应用自行处理分帧、部分发送 | 每个数据报承载完整一帧 |
| 故障处理 | 检测断开并约每秒重试；超时旧连接允许替换 | 无 TCP 连接状态或重连；发送错误计入 `send_failures`，不重放当前失败包 |
| 上位机关闭 | 观察到断线、重试及恢复 | 板端继续发送，恢复监听接收后续报文；停机期间遗漏不补发 |
| 交付边界 | TCP 提供连接内有序可靠字节流；本协议没有应用 ACK/序号，跨断线仍不能承诺绝不丢失/重复 | 可能丢失、重复或乱序，本任务没有应用重传 |
| 时延结论 | 当前 Wi-Fi 存在心跳到达抖动 | 仍存在抖动；不能由迁移或不同轮次短测断言更快 |

TCP 断线时未消费按键留在有界队列，恢复后可能收到旧事件；已经取出且发送结果不明确的帧记为 `uncertain`，不自动重放。退出须检查 `pending/uncertain`。UDP 除队列汇总外还要检查发送失败数与接收端计数，不能只看 `status=OK`。需要业务级可靠交付时，事件序号、确认、去重及重放策略属于后续扩展，当前未擅自改变原协议。

## 7. 关键问题、修正与尚不能下的结论

### 7.1 TCP 本机断线发现慢

旧版仅靠 Socket 读写/超时，关闭 Wi-Fi 后内核仍可能暂时接受发送，首次发现耗时 5820ms。增加每 100ms 只读检查连接本地 IPv4 是否仍属于 UP 接口后，同类实验为 101/96ms。细化观测中，首次观察到目标 Wi-Fi 与 IPv4 就绪至 TCP 建立约 449ms；观测周期约 100ms 加查询开销，不能外推所有条件下均在 1s 内恢复，也不证明远端静默丢包都能在 100ms 内发现。

### 7.2 同步日志阻塞与采集方式干扰

旧版出现接收→日志写完 65.568ms，原始超差保留。在无网络日志对照中，PowerShell 标准输出采集路径曾出现 134.4854ms，同样标准输出直接接文件句柄最大 4.169ms。说明输出路径会影响测量，不能直接归因于网络或业务计算。

修正采用有界异步日志与直接本地文件输出，仍统计实际写完。测试刻意阻塞输出超过 80ms，确认最终指标会保留超差而非用“异步入队快”掩盖它。修正后短测达标是当前证据，不是长期最坏时延保证。

### 7.3 心跳到达抖动仍未解决

TCP 真实按键轮次：板端 110 心跳、发送间隔 999–1001ms，Windows 109 个间隔为 801.289–1266.579ms，其中 10 个超出 900–1100ms。UDP 三分钟轮次：发送 180/接收 180，板端间隔 999–1001ms，Windows 为 212.297–1646.604ms，25/179 超差。

配对抓包中板端出站周期稳定，而 Windows 应用之前的捕获点已经出现抖动；同一 Windows 时钟下，原生无线捕获点到 Ethernet 捕获点仅 0.014–0.061ms。证据将该批主要抖动缩小到更早的无线链路或端点处理环节，仍不能区分板端固件、AP、空口竞争和 Windows 捕获点之前的驱动等待。

接收间隔 = 发送间隔 + 本帧途中等待 − 上帧途中等待。因此稳定每秒发送也可能交替出现长、短到达间隔。没有证据认定 RK3568 性能不足，也不能仅凭信号强就排除无线排队。TCP ACK 往返时间含返回路径和延迟 ACK，不能代替单向时延；两机未精确同步，也不能直接相减两端时间戳。

板端相关省电项已处于关闭状态。已授权的 Windows 无 SMPS 短对照未改善，随后恢复自动 SMPS；恢复后的 30 心跳正常不覆盖此前失败样本。当前继续原网络，不用额外填充流量、改心跳频率或放宽阈值冒充修复。详细分析见 [归因记录](tcp-root-cause-analysis.md)。

### 7.4 部署和测试本身也需核对

早期串口粘贴传输哈希失败，后采用小块确认和完整 SHA-256 校验，再通过已授权 SSH/Wi-Fi 部署。只看到文件存在不足以证明传输正确。UDP 源文件曾遇共享锁/缓存视图问题，采用带哈希保护的待应用副本，由 Ubuntu 应用、构建；板端运行和产物证明 UDP 分支有效，后续仍需核对共享源码视图一致性。

UDP 停发测试最初错误假定“三秒必发三个心跳”，已改为核对实际发送数量。真实按键首轮窗口没有采到事件，随后延长窗口才取得 4/4。失败、零事件与原始超差记录均保留，不将测试脚本假设或缺失样本当成产品通过证据。

### 7.5 UDP 真实断网：恢复通过与 INCOMPLETE 可以同时成立

有效复测见 [UDP 真实断网记录](udp-outage-validation.md) 和 [机器可读结果](../logs/udp-outage/20261122-192229/outage-result.json)。控制日志同时出现 `Not connected.` 与空 IPv4，离线观测约 8008ms 后请求恢复，随后回到原网络和地址。Windows 距最后有效心跳 2001.129ms 报警，恢复后继续接收心跳及 174 条合成按键。发送结束后另一次 2013.128ms 报警来自正常停发，不是再次掉线。

全程入队 273 个合成按键，其中 229 个 `sendto` 成功且 Windows 收到 229 个，44 个本地发送失败不补发；47 个成功发送的心跳全部收到，另有 9 个心跳发送失败，总失败数为 53。程序持续运行至预定时限，恢复后继续发送，最终 pending=uncertain=0。退出码 1、状态 INCOMPLETE 是对未全部交付事件的报告，不能改记为全程无丢失，也不能据此认定程序崩溃。UDP 沿用原数据报 Socket 恢复发送，没有 TCP 式重连。

本轮 276 条报文日志均 ≤50ms，最大 1.907ms；含状态日志 accepted=written=280。首次观测链路/IP 就绪到下一次成功发送为 102ms，这是同板观测值，包含就绪采样边界，不能当成单向网络延迟或立即接收的精确证明。此次使用合成按键，不替代物理按键响应测量。

首轮 `logs/udp-outage/20261122-192057/` 因 SSH 后台启动编排返回超时，上位机被提前停止；板端实际已运行并自行恢复，因此该轮不作为完整验收。修正启动方式后在 `20261122-192229/` 完整复测通过，首轮证据保留。生产 UDP 程序没有为掩盖断网失败而修改。
