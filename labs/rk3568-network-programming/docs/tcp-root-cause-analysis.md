# TCP 时序问题归因：代码、输出路径与网络分别判断

日期：2026-11-22。依据原始任务 4.1 步骤 4、5.2，本轮只做分析与对照，不修改生产版 Receiver.cs、key_network.c、网络配置或验收阈值。

## 先分清原文指标

| 原文位置 | 起点→终点 | 阈值 |
| --- | --- | --- |
| 4.1 心跳验证 | 相邻心跳日志的时间间隔 | 1s，误差 ±100ms |
| 4.1 按键事件验证 | 按键按下→上位机显示按键事件 | ≤100ms |
| 5.2 按键检测响应 | 物理按下→消息入队 | ≤50ms |
| 5.2 网络传输延迟 | 板端发送→上位机接收并解析 | ≤100ms |
| 5.2 日志打印实时性 | 上位机接收→日志打印完成 | ≤50ms |

两个 50ms 属于不同环节，不能把它们解释为整个按键到 Windows 链路统一 ≤50ms。此前 65.568ms 指接收→日志写完，不是按键消抖→入队。原始 Word 已再次只读核对，用户截图与正文一致。

## 结论一：旧版本机断线发现慢属于可改进的代码策略，已经修正

关闭本机 Wi-Fi 后，TCP Socket 仍可能在一段时间里接受 send，只是数据进入本机缓冲；这不代表对端收到。旧实现只靠 Socket 读写/超时观察，没有及时检查本机网络已消失。

在 key_network.c 中增加每 100ms 检查本地 IPv4 是否仍属于 UP 接口后，同样的短断网测试由 5820ms 缩短到 101/96ms。这是修改代码带来改善的直接证据，但只适用于本机接口/地址消失，不等同于远端静默丢包都能 100ms 发现。

## 结论二：日志超差能在无网络条件下复现，输出采集方式有明显影响

检查 Receiver.cs：Socket.Receive、Parser.Feed、Log、心跳超时判断在同一线程。Log 同步调用 Console.WriteLine。输出阻塞会暂停这个线程，这是代码的结构性薄弱点。

本轮新增 tests/LogPathProbe.cs，分别测量同样内容的字符串格式化和 WriteLine。每种方式 1000 次，间隔约 2ms；保存所有样本，同时单独统计排除前 10 次初始化后的结果。它是日志路径诊断，不冒充正式 1Hz 网络验收。

| 路径 | 所有样本 WriteLine 最慢 | 预热后最慢 | 超过 50ms 次数 |
| --- | ---: | ---: | ---: |
| 空输出（不写系统输出设备） | 0.0106ms | 0.0106ms | 0/1000 |
| C# 直接写本地文件，AutoFlush=true | 17.5603ms | 1.1634ms | 0/1000 |
| 标准输出 Console.Out.WriteLine，经 PowerShell Start-Process 重定向 | 134.4854ms | 134.4854ms | 1/1000 |
| 同样的 Console.Out.WriteLine，标准输出直接接文件句柄 | 4.1690ms | 4.1690ms | 0/1000 |

最慢的 134.4854ms 样本中，字符串格式化只有 0.0363ms；输出阶段当前线程累计约 449195 个 CPU 周期。不能将这些周期直接换算为准确 CPU 用时，但相对于很长的墙钟时间，它支持等待/调度影响，而不是字符串算法连续计算 134ms。尚不能精确分开管道背压、父进程读取、锁等待和调度暂停各占多少。

这也是对之前诊断的补充：此前所有正式 Windows 测试均通过 PowerShell Start-Process -RedirectStandardOutput 采集日志，该启动/采集路径本身会影响被测时间。65.6ms 的读数是真实的该次调用经过时间，却不能直接推出业务代码计算慢或 Wi-Fi 导致日志写入慢。

## 结论三：不改原程序源码，只换输出句柄，正常 1Hz 联调也得到改善

使用同一个 Receiver.exe、同一个板端程序、同一 Wi-Fi 和相同协议，改由直接文件句柄收集标准输出，发送 25 个心跳：

- Windows 收到 25 个心跳，无按键输入。
- 接收→完整日志写入调用返回，最大 4.462ms。
- Log 本身最大 2.674ms，解析最大 3.518ms。
- 心跳到达间隔仍为 875.565–1127.193ms，超出 ±100ms 的样本没有随日志路径改善而消失。

证据位于 logs/root-cause/direct-receiver。对照支持日志路径是重要影响因素，但顺序实验受当时系统负载影响；25 个心跳不足以承诺长期最坏情况永远 ≤50ms。它也不能追溯证明之前某一次 65.6ms 的所有内部等待来源。

目前 max_receive_to_log_ms 的精确定义是应用 Socket.Receive 返回→Console.WriteLine 返回；不包含读取之前的内核排队，也不证明磁盘持久化或屏幕实际绘制完成。后续验收须固定这个测量口径，若需要 UI 可见延迟则另行测量。

## 结论四：已有心跳到达抖动主要位于应用解析之前

已有配对抓包 logs/timing3 中，同一批心跳：板端出站间隔为 999.184–1000.836ms；Windows WFP 802.3 捕获点间隔为 890.562–1075.583ms。后者在应用代码之前，已出现抖动。Windows 应用日志与它基本一致。

这支持：当前样本不是 C 心跳定时器本身抖动，也不是 C# 校验六字节报文算得太慢。board key_network 已使用单调时钟、绝对周期、非阻塞 Socket、TCP_NODELAY，并且抓包验证了出站周期。不能因此宣称全部源码完美，只能排除这些环节作为该批抖动的主要解释。

应用之前仍包含：板端抓包点之后的无线驱动/硬件、AP 转发/排队、无线介质竞争与重传、Windows 无线驱动至捕获点。两端同一 2.4GHz AP，不能据此在没有对照的情况下把具体根因锁定为路由器、无线干扰或某一种省电设置。信号强、速率显示正常也不能排除排队和干扰。

若第 n 帧发送时刻为 S_n、途中等待为 D_n，接收时刻 R_n=S_n+D_n，则接收间隔等于发送间隔加 D_n-D_(n-1)。即使每次恰好间隔 1000ms 发送，某一帧额外等 180ms，就会形成约 1180ms，后面一帧可能形成约 820ms；这不是发送端突然加快了心跳。

TCP_NODELAY 已启用，所以不宜首先归咎于发送端 Nagle 合并。抓包未见这批板端心跳的 TCP 重传，不等于排除 Wi-Fi 链路层重传。数据→ACK RTT 包含返回路径和延迟 ACK，不等于单向延迟。两机未精确同步，不能用报文中秒级时间戳证明 ≤100ms 单向传输。

65.5ms 的慢日志发生在 heartbeat=2：该帧的 1186.308ms 到达间隔在进入 Log 前已经计算完成。因此这次慢写日志不可能倒过来造成同一帧已经测出的长到达间隔。它有可能影响后续接收，不能把两种现象混成同一个根因。

## 代码仍有需要改善的地方，但应区分已证实与潜在风险

1. Windows 接收与同步输出耦合；板端网络线程也有同步 printf。输出一旦变慢，会暂停对应业务线程。后续应将关键处理与日志写入解耦，使用有界队列并明确满队列策略，避免无限增长或悄悄丢日志。
2. 异步日志入队快，不等于“日志打印完成”快。验收必须包含排队与实际输出完成耗时，不能通过改变计时终点获得虚假的 ≤50ms。
3. 代码同时把连接重试间隔和单次 connect 等待限度设为 1000ms。这两个概念不同，短连接限时可能与首次 SYN 重传时间竞争，是应独立复核的策略风险；尚无证据证明它就是之前某次 2.07s 恢复的根因。
4. 按键消抖使用约 2ms 采样加至少 10ms 稳定窗口，既有软件观察→入队约 11–12ms。物理触点→驱动报告的时间未测，不能把软件观察值当成完整物理延迟已经通过。

优先次序：固定低干扰的输出采集方式并重复正式样本；改善同步日志耦合；随后做受控无线链路对照以缩小应用前抖动来源。无需为这些问题重写消息队列/消抖，也不应通过改成 UDP、过滤异常样本或放宽阈值假装已经达标。本轮保持生产源码及网络配置不变，未启动 UDP 或一小时稳定性测试。
