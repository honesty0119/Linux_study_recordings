## 实现与理解

开发板主线程约每 2ms 采样按键，并读取 evdev 边沿；按下和释放都需稳定至少 10ms。只有新按下被封装为原协议 8 字节帧，经 System V 消息队列送给网络线程。持续按住不会重复入队。

网络线程独占 TCP Socket，处理非阻塞连接、部分发送、断开及约每秒重试。每秒心跳用单调时钟调度，队列无消息也不会停止心跳。消息队列用于线程解耦，不要求本实验一定拆成两个进程。

Windows C# 接收端保留半帧、连续解析合帧，验证类型、按键字段及 XOR；非法帧关闭该连接，继续监听。仅有效心跳重置两秒计时，普通按键不能掩盖心跳中断。原文允许 C# 上位机；板端主程序使用 C，Python 仅用于自动测试和原始输入诊断。

- 用户反馈 Ubuntu 本机检查和交叉编译通过；截图确认 ARM64 ELF。经已授权的 SSH/SCP 上传，源与板端 SHA-256 一致。
- 板端协议/消抖测试 24 项通过；Windows 接收端自测 28 项通过。

- 真实 Wi-Fi 两轮合成输入均为 43 个入队、43 个发送、43 个接收；首轮心跳接收间隔约 972–1070ms，第二轮约 965–1030ms；心跳停止后约 2.00s 报警。
- 关闭及重启上位机，开发板观察到断开并继续重试，服务恢复后重新接收心跳。自动测试最初仅接受“连接拒绝”日志，实际是“连接超时”，已修正测试预期并重新运行通过；两种结果都可能发生在未监听时。

- 驱动事件被诊断程序观察到至入队约 11–12ms，仅为软件观察值，不是物理触点到入队的完整延迟。不同机器的单调时钟不能直接相减求网络延迟。

## 深入归因：区分代码与测量环境

- 再次只读核对原文及用户截图：4.1 心跳间隔误差 ±100ms、按键到显示 ≤100ms；5.2 分别规定物理按下→入队 ≤50ms、发送→接收解析 ≤100ms、接收→日志完成 ≤50ms。不能把三个环节混为一个 50ms 总指标。
- 审查发现 Windows 收包、解析、同步日志和超时判断在同一线程，输出阻塞会暂停业务处理；板端网络线程也有同步 printf。这是代码设计的薄弱点，不能把全部问题推给无线。
- 用四种日志输出路径、每种 1000 样本进行无网络诊断。空输出最慢约 0.011ms；程序直接写文件最慢 17.56ms（预热后 1.16ms）；经 PowerShell 标准输出重定向最慢 134.49ms；相同标准输出直接接文件句柄最慢 4.17ms。没有从此单次顺序实验推导永远的最坏情况保证。
- 使用原接收程序、同一板端程序和网络，改用直接文件句柄，正式 1Hz 的 25 个心跳最大接收→日志完成为 4.462ms；心跳到达间隔仍 875.565–1127.193ms。因此日志采集方式是重要影响因素，且不能解释全部应用前到达抖动。
- 原有配对抓包支持出站周期稳定，而 Windows 应用之前已有抖动；没有将无线/AP/驱动中的某一项冒称为已确定的唯一根因。慢日志发生在到达时间计算之后，也不能倒因果解释同一帧此前已经发生的到达延迟。
- 本轮未修改生产源码或网络；实验已退出、队列为空。归因报告和原始对照 CSV 保存在 task2/docs/tcp-root-cause-analysis.md 与 logs/root-cause。建议先固定低干扰输出采集，再改善同步日志耦合，最后做受控链路对照。未把日志入队快当成打印完成快，未放宽验收阈值或发布记录。
